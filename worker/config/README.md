# Настройки агента на хосте

Секреты здесь не лежат. Их держат в `/etc/ai-family.env` на машине воркера: ключ Cursor, GitHub, Telegram, Supabase и закрытый бакет Hetzner для фотографий и входящих вложений.

Повторить на новом хосте:

1. Установить Node.js 22 и Cursor CLI. Создать пользователя `ai-family`, каталоги `/opt/ai-family-runtime/` и `/var/lib/ai-family/` с правами этого пользователя.
2. Положить секреты worker в `/etc/ai-family.env` (root:root, 0600), а только `SUPABASE_URL` и `SUPABASE_ACCESS_TOKEN` — в `/etc/ai-family-deploy.env` (root:ai-family, 0640). Перенести Cursor CLI и настройки в `/home/ai-family/`, затем выполнить `scripts/install-agent-config.sh` от имени `ai-family`.
3. Создать `/opt/ai-family-runtime/source` как рабочий Git-клон, `/opt/ai-family-runtime/releases`, ссылку `/opt/ai-family-runtime/current` на активный релиз. Установить root-owned `worker/ai-family-worker.service`; служба запускает код от `ai-family`. Разрешить этому пользователю через sudoers только `systemctl stop/start ai-family-worker.service`.
4. Пуш изменений `worker/`, `scripts/` или `supabase/migrations/` в `main` запускает тесты, затем GitHub Actions заходит как `ai-family` по отдельному SSH-ключу и запускает `scripts/deploy.sh` с SHA проверенного коммита. Ключ на сервере ограничен этой командой. Приватная половина лежит в секретах репозитория `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_KNOWN_HOSTS`. Повторная ручная выкладка запускается через `workflow_dispatch` того же workflow. Для перехода со старой root-схемы есть однократный `scripts/bootstrap-unprivileged.sh`.

`cli-permissions.json` разрешает веб-поиск, чтение страниц, `git`, файлы рабочей папки и MCP GitHub. Чтение `.env` и `rm` запрещены.

Сессии диалогов — каталог `/var/lib/ai-family/chats/` на хосте. Личный чат — файл `user:<id>`, тема группы — `topic:<chat>:<тема>`. В файле id чата Cursor, `startedAt` и `updatedAt`. Это состояние машины, в git его нет. Воркер создаёт отдельную рабочую копию проекта для каждого контекста в `/var/lib/ai-family/repos/contexts/` и обновляет её перед заданием. Личные диалоги используют `/var/lib/ai-family/workspace/contexts/`. Входящие вложения и геометки сохраняются в Hetzner Object Storage при запуске задачи; ключи объектов остаются в `agent_jobs.artifacts`. Перед запуском агента файлы копируются в `inbox/` своей копии. Обычный Telegram Bot API разрешает скачивать файлы не больше 20 МБ; для больших файлов в записи остаётся причина недоступности. По умолчанию одновременно выполняется не больше трёх задач; лимит задаёт `MAX_CONCURRENT_AGENTS` в `/etc/ai-family.env`. Витрину выкладывает не этот репозиторий, а пуш в `main` репозитория проекта.

Запуск агента ограничен 30 минутами (`AGENT_TIMEOUT_MS` в миллисекундах). Если время вышло, воркер останавливает процесс и повторяет задачу в прежнем контексте до трёх попыток, удерживая порядок сообщений в этой ветке. GitHub Actions не запускает одновременно две выкладки воркера, а сервер дополнительно держит блокировку `/opt/ai-family-runtime/deploy.lock`. Скрипт собирает релиз в `/opt/ai-family-runtime/releases/<SHA>`, переключает `/opt/ai-family-runtime/current` только после установки зависимостей и возвращает предыдущую ссылку, если новый worker не запускается. Unit systemd принадлежит root и при изменении требует отдельной проверки администратором. Состояние диалогов и рабочие копии остаются в `/var/lib/ai-family/`.

Перед переключением релиза deploy применяет новые файлы `supabase/migrations/*.sql` через Supabase Management API. История хранится в `public.ai_family_schema_migrations` с SHA-256 каждого файла. Изменение или удаление уже применённой миграции останавливает релиз; новую схему записывайте отдельным SQL-файлом с возрастающей 14-значной версией. Для доступа нужен `SUPABASE_ACCESS_TOKEN` в `/etc/ai-family-deploy.env`. При ошибке миграции старый worker остаётся работающим. После успешной миграции откат кода не откатывает базу: миграции должны быть совместимы и со старой версией worker.

Worker обновляет `/var/lib/ai-family/worker-heartbeat.json` каждые 10 секунд. Deploy проверяет свежий сигнал именно от нового PID перед признанием релиза здоровым. Отдельный systemd timer `worker/ai-family-health.timer` запускает `worker/ai-family-health.service` каждые две минуты и проверяет сигнал, процесс и Telegram-очередь. Он предупреждает в Telegram, если задача ждёт более 10 минут без работающего агента или один запуск длится более 40 минут. Повторное предупреждение по той же причине приходит не чаще раза в час, после восстановления приходит одно сообщение. Адресат задаётся `TELEGRAM_ALERT_CHAT_ID` в `/etc/ai-family.env`; если он не задан и в `TELEGRAM_ALLOWED_USER_IDS` ровно один пользователь, уведомление идёт ему. Unit и timer принадлежат root: их устанавливают один раз и обновляют отдельно после проверки.

Фоновый обход Белграда работает двумя независимыми обработчиками внутри worker: поиск и проверка общей очереди. Поиск начинает полный проход `scan.json` каждые 12 часов и продолжает сохранённый проход после перезапуска. Проверяющий берёт по одному старому или новому объявлению и переходит к следующему через общий ограничитель частоты; если готовых объектов нет, ждёт новое поступление или наступление срока проверки. Каждая попытка отмечается до открытия страницы, повтор возможен не раньше чем через 24 часа. Новые объекты разбираются в собственном контексте `scan:belgrade-apartments:check` и рабочей копии, независимо от Telegram. Лимит новых разборов — 100 в день по времени Белграда, старых проверок — без дневного лимита. Состояние лежит в `/var/lib/ai-family/scan-state.json` (`SCAN_STATE_PATH`); очередь и курсор поиска записываются атомарно, старый формат переносится без обрезания ссылок. После перезапуска прерванная проверка остаётся в очереди с прежним сроком в 24 часа. `SCAN_EVERY_MS` больше не используется: для обоих обработчиков действует общая пауза не менее 60 секунд между обращениями к сайтам и запусками нового разбора. Время последнего обращения сохраняется в состоянии, поэтому перезапуск не сбрасывает паузу.
